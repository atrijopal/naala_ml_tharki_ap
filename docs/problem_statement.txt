Evaluation Rubric
01
Background
Every group outing — hostel mess bills, canteen orders, restaurant dinners — ends the same way: someone pulls out a phone, squints at a crumpled bill, and an argument breaks out over who owes what. "I didn't have the paneer" is a universal sentence.

The math isn't hard; the information extraction and fair attribution are.

The SplitSnap Challenge:
SplitSnap asks teams to build a system that takes a single photo of a bill and produces a correct, explainable, person-wise split — handling shared items, partial consumption, taxes, service charges, and discounts properly, not just dividing the total by the headcount.

02
Problem Statement
Build an end-to-end application that delivers all six core capabilities:

1
Accepts a Photo of a Receipt
Takes a camera capture or upload of a restaurant or canteen bill.

2
Self Fine-Tuned Vision Model Extraction
Extracts structured data from the photo: items, quantities, prices, taxes, discounts, and total.

3
Named Member Party Assignment
Lets a user add all party members by name and assign items to them (including shared and partial items).

4
Proportional Math Apportionment
Computes a correct final split by proportionally distributing tax/service charges/discounts based on pre-tax subtotal shares, not just splitting them equally.

5
Plain-Language Split Explanation
Explains, in plain language generated by the model/pipeline, exactly how each person's final amount was arrived at.

6
Manual Correction & Split Override
Allows manual correction of OCR mistakes and manual override of the computed split before finalizing.

Core Evaluation Philosophy:
The team's job is not "call an API and build a UI" — it is to own the extraction model and build the correction, explanation, and attribution logic around it properly.

03
Mandatory Requirements (R1 – R8)
R1 — Self Fine-Tuned Extraction Model
Mandatory (No Off-the-Shelf)
Teams must fine-tune a model themselves on the provided datasets (CORD + SROIE) rather than only prompting a pretrained model out of the box.
Acceptable base architectures: Any open-source OCR / document-understanding model — e.g. Donut, LayoutLMv3, PaddleOCR + custom head, TrOCR, or open VLMs (Florence-2, LLaVA, Qwen-VL) adapted on the receipt data.
Strict prohibition: Simply prompting a pretrained model with no training/fine-tuning step (e.g. zero-shot API calls) does not satisfy this requirement.
Mandatory proof in submission: Teams must show training/fine-tuning scripts, chosen train/val/test splits, loss curves or eval metrics before vs. after fine-tuning, and a note on base model selection.

R2 — Bonus: Advanced-Tier Handling via Confidence Scores
+15% Bonus Marks
Base requirement: Handles clean, well-lit, standard-layout bills.
Bonus points for handling the "advanced tier": Blurry/tilted photos, faded thermal print, handwritten totals, and non-standard layouts.
Rewards confidence-driven behaviour: the model outputs per-field confidence scores, and fields below threshold are automatically flagged in the correction UI.
Bonus scoring criteria: Real correlation with error rates, clean UI treatment of low-confidence fields, and graceful retake prompts on degraded images.
R3 — Manual Correction UI
10% Weight
No OCR pipeline is 100% accurate — manual correction is expected and necessary.
Provide a UI where extracted items, prices, and charges are editable before splitting: add missed items, fix wrong prices, delete hallucinated lines, and correct misread quantities.
Corrections must propagate into the final mathematical split.
Low-confidence fields from R2 should be visually highlighted in this correction interface.
R4 — Open-Source Only (Strict Pass/Fail)
Strict Pass / Fail
Only open-source models and OCR/VLM systems are allowed for the extraction pipeline — no closed/paid APIs (e.g. no GPT-4V, Gemini, Claude vision API calls).
Keeps the challenge fair across all teams and tests genuine model-building capability.
Acceptable families: Donut, LayoutLMv3, TrOCR, PaddleOCR, EasyOCR, open VLMs (Florence-2, Qwen-VL, MiniCPM-V).
R5 — Separate Identification and Display of All Charges
10% Weight
Distinguish item lines from non-item lines: CGST, SGST, VAT, service charges, packaging fees, discounts, and rounding adjustments.
Display charges distinctly: Items: ₹X, Taxes: ₹Y, Service Charge: ₹Z, Discount: -₹W, Total: ₹T.
Show transparently how each non-item charge is distributed across people in the final split.
R6 — Explained Splitting Logic (Per Bill)
10% Weight
Produce a human-readable explanation of the split logic for every bill processed (pipeline-templated or model-generated).
Must detail: which items each person is charged for, how shared items were divided, proportional tax/discount distribution, and the final owed total.
"Riya: Paneer Butter Masala (full, ₹220) + 1/3 share of Garlic Naan (₹40) = ₹260 subtotal. Tax + service charge apportioned at 12.9% of subtotal (based on her share of the pre-tax bill) = ₹33.5. Final: ₹293.5."
R7 — Override Option
5% Weight
Users must be able to manually override any person's final amount or item assignment after computation.
Overrides must be clearly flagged as manual adjustments in the final summary.
R8 — Flexible Party Size and Named Members
5% Weight
Allow an arbitrary number of named individuals per bill (not just anonymous numbers).
Dynamic member addition/removal before and after initial item assignment.
Participant names must carry through into the final summary and plain-language explanation.

Datasets (Provided)
Dataset	Primary Use	Notes & Annotations
CORD
(Consolidated Receipt Dataset)	Fine-tuning item / price / total extraction	Labelled with entity-level annotations (menu items, prices, subtotal, tax, total).
SROIE
(Scanned Receipts OCR & Extraction)	Fine-tuning + OCR robustness	Company, date, address, total — especially useful for separating charges from items.
Organizers Provide Data: Core labelled data comes from CORD and SROIE.
Augmentation Policy: Teams may supplement with light synthetic augmentation (rotation, blur, brightness jitter, partial occlusions) to simulate the advanced tier.
Domain-Gap Disclosure (Important — Read Carefully):
CORD and SROIE are largely retail/grocery receipts from international contexts — they do not look like Indian restaurant or hostel canteen bills (different layout, no GST-style tax lines, distinct naming).

Teams are expected to fine-tune on CORD/SROIE for core entity extraction, and demonstrate generalization on a small held-out set of real Indian bills during final evaluation.

Compute Guidance (Free-Tier Colab)
Fine-tuning is mandatory (R1), so teams need a realistic compute plan. Between the two viable free options, Kaggle Notebooks is the recommended primary platform: it offers a guaranteed 30 GPU-hours/week (fixed quota, not demand-based), a choice of a single P100 (16GB) or two T4s (32GB combined), 20GB persistent storage, and no credit card requirement. Google Colab free tier (T4, 16GB VRAM) is a solid secondary/backup option, but its 15-30 GPU-hours/week is allocated dynamically based on platform demand - meaning availability can dip right when a room full of hackathon teams needs it most. Plan your compute budget around Kaggle as the default, with Colab as overflow.

import torch
from transformers import DonutProcessor, VisionEncoderDecoderModel
from torch.utils.data import Dataset, DataLoader
from PIL import Image
import json

# 1. Load Pretrained Open-Source Base Model (Donut-base or Florence-2)
model_name = "naver-clova-ix/donut-base"
processor = DonutProcessor.from_pretrained(model_name)
model = VisionEncoderDecoderModel.from_pretrained(model_name)

device = "cuda" if torch.cuda.is_available() else "cpu"
model.to(device)

# 2. CORD / SROIE Dataset Loader with Indian GST Prompt Formatting
class ReceiptExtractionDataset(Dataset):
    def __init__(self, metadata_path, img_dir, processor, max_length=768):
        with open(metadata_path, 'r', encoding='utf-8') as f:
            self.records = json.load(f)
        self.img_dir = img_dir
        self.processor = processor
        self.max_length = max_length

    def __len__(self):
        return len(self.records)

    def __getitem__(self, idx):
        item = self.records[idx]
        image = Image.open(f"{self.img_dir}/{item['image_id']}").convert("RGB")
        pixel_values = self.processor(image, return_tensors="pt").pixel_values.squeeze(0)

        # Target JSON string representation for structured extraction
        target_seq = json.dumps(item['ground_truth'])
        labels = self.processor.tokenizer(
            target_seq,
            add_special_tokens=False,
            max_length=self.max_length,
            padding="max_length",
            truncation=True,
            return_tensors="pt"
        ).input_ids.squeeze(0)
        labels[labels == self.processor.tokenizer.pad_token_id] = -100

        return {"pixel_values": pixel_values, "labels": labels}

# 3. Fine-Tuning Setup on Free-Tier T4 (fp16 mixed precision)
optimizer = torch.optim.AdamW(model.parameters(), lr=5e-5, weight_decay=0.01)
scaler = torch.cuda.amp.GradScaler()

print("Fine-tuning pipeline ready for CORD + SROIE training!")

Constraints & Notes for Teams
Compute / time budget: Full CORD (~1,000 images) and SROIE (~1,000 images) can be fine-tuned in the available window on a single GPU; subsampling and using a smaller base model (e.g. Donut-base) is encouraged if time-constrained.

What "Winning" Looks Like
The best submissions will be the ones where, if you handed the app a real, slightly-messy hostel mess bill from your own campus that it had never seen, it would:

(a) Extract it mostly correctly,
(b) Let you fix the 1–2 things it got wrong in a few taps,
(c) Split it in a way every party member would look at and go "yeah, that's fair," and
(d) Explain why clearly enough that nobody argues about it afterward.
